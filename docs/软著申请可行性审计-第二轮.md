### 🔴 P1-new-1（**上一轮漏报**）　`docs/api.md` §9 描述的是**不存在的 API**

上一轮我只发现 `api.md` §4 有旧模型残留，且**误判为「已修正」**。本轮逐成员核对后确认：
**§9「桌面 UI（desktop 模块）」整节描述的是重构前的 API，没有一个成员对得上。**

| `api.md` §9 声称 | 实际代码 |

| `AppState.viewport` | **不存在**（`.viewport` 只存在于 `DrawBoxHost`） |
| `AppState.tools` | **不存在** |
| `AppState.importImage()` | **不存在**，实际是 `importImageBytes(bytes)` |
| `AppState.applyLocal(op)` | **不存在**，实际走 `host.onLocalIntent(...)` |
| `CanvasViewport(document, viewport, tools, docVersion, onOp)` | **不存在** |
| `FloatingToolBar(tools, onUndo, onRedo, canUndo, canRedo)` | 函数存在，但签名不同（首参为 `host`，无 `tools`） |

| `ConnectionPanel(...)` | 存在，但**缺少新增的 `codeIsRemote` / `shortCodeEnabled` 参数** |

`AppState` 的真实公开方法为：

setMode / setStrokeColor / setStrokeWidth / setOpacity / bringToFront / sendToBack /
deleteSelected / duplicateSelected / clearCanvas / commitTextEdit / dismissTextEdit /

> 同一节里 `api.md` §4 至少有「（注：上述为旧自研模型）」的免责说明，
> 而 §9 **没有任何标注**，读者会当作现行 API。这是申报材料里的实质性瑕疵。

**处理方式**：以 `AppState` 实际成员重写 §9；§4 若有保留价值则明确标注为历史设计，否则删除。

### 🟠 P1-new-2　README 的 TURN 说明在短码模式下容易被误读

> ✅ **已修复**（提交 `990f9a3`）。修复时发现根因比"措辞不一致"更基础：
> README 把**传输层**（TURN）与**配对信令层**（会合服务器）混在同一句话里，
> 而这两件事是正交的。已新增一节把两个服务器分开讲，并给受影响的两处补限定。

`README.md` 的"设计上为什么这么做"表中仍有一行：

> 加密通道只在两端之间 | …跨网时数据经你配置的 TURN 服务器转发。**它只转发密文，看不到内容**

这句话对 **TURN** 是准确的，但 README 同一页上方刚讲了短配对码。
读者容易把"看不到内容"套到**会合服务器**上——而会合服务器**恰恰具备替换公钥的能力**。

README 其实已在"配对方式的信任差异"表里说清了区别，但这两处相隔较远、措辞一强一弱。
`docs/protocol.md` §10 与 `user-guide.md` §9 的表述是准确的。

**处理方式**：在 TURN 那行补一句限定（如"（仅指 TURN；会合服务器的信任差异见上表）"），
使两处口径在同一屏内自洽。

**实际修复内容**（比原计划更彻底）：

1. TURN 那一行补上限定：「**仅指 TURN——会合服务器的信任差异见下一节**」。
2. 新增小节「⚠️ 两个"服务器"别混淆（重要）」，用一张表把 **TURN 中继**与**会合服务器**
   并列对照：是否必需、能做什么、看不到什么；并点明关键区别在**信令层**（公钥由谁下发）
   而非**传输层**（数据怎么传）。
3. 开头「没有中心服务器」那句补一条限定，说明它描述的是**默认扫码直连**路径，
   并指向上述新小节——避免"开头承诺 / 后文推翻"。
4. 原「配对方式的信任差异」小节标题改为「配对方式的信任差异：公钥由谁下发」，
   与前一节区分，不再两节同以"别混淆"结尾。

> 顺带核实：开头那句「没有中心服务器」本身**无歧义、且对扫码路径准确**——
> 它不含"看不到内容"这类安全声明，原报告将其列为问题偏保守，此处更正描述。

### ✅ P1-new-3　申报口径：**已定为「一件软件含信令子系统」**

> **决策已下**（申请人确认）：采用下文的**方案 A**。
> 即会合服务作为同一件软件内的**配对信令子系统**，与 Kotlin 客户端合并申报。

本仓库现含**两个可独立运行的程序**：

| 组件 | 语言 | 主代码体量 | 性质 |
|---|---|---|---|
| Juan LinK 客户端 | Kotlin | 8,056 行（core 4,478 / composeUi 2,746 / desktop 320 / androidApp 512） | 主软件 |
| 会合服务 | Python | 514 行（`server/`） | 配对信令子系统 |
| 维护工具 | Python | 403 行（`tools/`） | **非产品代码，不纳入** |

软著登记以"一件软件"为单位。两种做法的取舍：

- ✅ **方案 A（已采纳）**：作为**一件软件**申报，例如软件全称
  「**Juan LinK 端到端加密点对点协作画板软件**」（版本 V1.0），
  在"主要功能和技术特点"中把会合服务描述为其中的**配对信令子系统**。
  交存源程序时把 Kotlin 客户端与 Python 服务端一并纳入（均为自有代码）。
- ❌ 方案 B（未采纳）：拆成两件分别登记。会合服务仅 514 行、功能单一
  （短码登记/查找 + 限流），**单独申报偏薄**。

> ⚠️ **名称写法必须统一为 `Juan LinK`（大写 K）**。
> 代码中 `AppInfo.APP_NAME`、README 标题、窗口标题均为此写法（出现 59 次），
> 而仓库中另有 1 处误写作 `Juan Link`。交存源程序页眉已按 `Juan LinK V1.0` 生成。

**三处口径必须一致**：申请表"软件名称/主要功能"、交存源程序页眉、用户手册页眉。

⚠️ **`tools/` 不应纳入交存范围**——它是仓库维护脚本（含绕过网络封锁推送 GitHub 的说明），
与软件功能无关。写进申请材料反而会让审查员困惑于"这软件到底做什么"。
若担心混淆，可在提交前把 `tools/` 暂时移出打包目录。
